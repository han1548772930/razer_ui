# 工程决策与诊断

本规则适用于根程序、全部 crate、维护工具、生成器、测试和安装配置。范围与执行限制以根目录 `AGENTS.md` 为准。

- 遵守根目录的独立实现要求：官方 DLL 只作为逆向证据与显式功能对照对象，不能作为产品后端。先核实完整功能链、修正架构并实现 Rust 所有者，再迁移全部调用方和清理厂商加载依赖；不得以导出包装、IPC 转发、改名或仅登记缺项交付。

- 先把问题描述拆成可核验的现象、预期行为和原因假设；用户报告或审查结论是调查起点，不能直接当作根因。核对当前代码和最直接的当前原件，记录首个出现差异的边界。
- 沿发现／打开、传输、协议解码、服务状态、IPC、领域状态、界面选择和呈现逐层定位。接口存在、通道可用、能力已观测、设备在线和设置已写入分别判断；一层成功不能证明下一层成功。
- 在真正拥有状态、决策或生命周期的模块修复根因。开发环境故障在环境边界解决，不给产品叠加绕过、静默回退或单次特例。
- 同一决策只有一个所有者。准备写第二份编码、版本判断、路由、阈值、选图或重试策略时，先核对语义；相同则共用所有者输出的有类型结果，有差异则查明产品／版本依据。不能仅公开原料让各调用方重新推导规则。
- 合并公共规则时同步迁移所有调用方、生成器和清理路径，并在统一维护入口加入结构检查。检查应指出真正的所有者，验证禁止的副本会失败、合法所有者与无关代码会通过；未实施的检查不得描述为已有保障。
- 先找已有成熟依赖和项目入口，再增加实现或依赖。模块按独立语义与生命周期划分，文件长度和重复率用于发现问题，不能成为机械拆文件、堆包装层或新增 crate 的理由。
- 平行任务明确文件与状态所有者；共享边界先沟通，读取当前差异后接续。不得覆盖其他任务的修改，也不得把中途编译失败归为既有问题而跳过接线。
- 逆向批次必须按根目录 `AGENTS.md` 第 7.1 节完成清理闭环。创建临时克隆、数据库和中间文件的流程拥有正常、失败、取消及释放责任；正式证据校验与依赖接线完成后，及时清除已无用途的副本，避免留到下轮累积。清理仍由统一维护入口核实并执行，不得绕过活动会话和真实依赖保护。
- 参考工程只提供方法与架构线索。协议、默认值、产品能力、界面行为和成功语义必须由当前 Razer 原件证明；证据获取、分析、实现、模拟验证与真实验收分别记录于现有工作流。
