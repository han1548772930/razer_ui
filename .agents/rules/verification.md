# 验证、维护工具与交付输入

- **所有功能必须测试并进行官方实际对照**：所有范围内功能均须有自动化行为测试，按产品、固件、传输和平台分支覆盖正常、边界、未知值、失败、取消、重连及清理等适用路径。功能清单逐项连接当前官方来源、Rust 所有者、调用方、测试用例和实际对照收据，不能由同族型号、局部 getter 或整个 crate 编译通过推断其余功能已验证。
- **全部页面与交互同样逐项核对**：范围内每个产品／版本／配件分支的实际页面、导航、布局尺寸、资源、文案、弹层、提示、键盘／焦点、加载／空／错误／禁用状态，以及挂载、切换、取消与释放均须对应当前官方 JS／CSS 的完整所有者和 Rust 生产消费者，并有适用的自动化状态／行为验证。静态声明、组件名、扫描计数、预览页和模拟通过不能代替实际挂载树或视觉验收；按根目录执行限制不能运行的窗口验收保持未验证。页面设备动作继续遵守下述实际 DLL 对照要求，不能用 DLL 返回值证明像素或焦点一致。
- **官方 DLL 必须实际执行对应功能**：将独立 Rust 实现与经核实的当前官方 DLL 在相同输入、明确的版本和受控初始状态下执行的对应功能结果逐项比较；按功能记录原始返回、类型化结果、状态与副作用、应答／读回、事件及其顺序、失败、取消、恢复和释放。不得只检查加载、导出调用成功、相同错误码或两边均未连接。UI／前端行为同时依据当前官方 JS／CSS 验证，其设备／服务动作继续追到实际 DLL 功能结果；仅在完整官方链已证明没有对应 DLL 行为时记录依据和实际比较边界，不得虚构导出或绕过已有 DLL 链。
- **官方 DLL 只用于显式对照**：普通启动、页面和纯测试不得加载官方业务 DLL；对照统一从 `tools/workspace.py` 的独立维护入口运行，先核实来源、实际字节 SHA-256、版本、架构、ABI、依赖及初始化／释放链，严禁猜测签名。生产路径保持独立 Rust 实现，生产依赖是否已删除单独核验；对照 worker 不得成为产品后端。
- **无设备也必须完成可执行测试**：通过现有传输／服务接口实施脚本式模拟、故障注入和有依据的应答回放；无需硬件的官方计算、编码和文件处理等功能，在核实可独立执行后继续做实际 DLL 差分测试。依赖真实设备、驱动或服务而无法执行的对照分别保留“未验证”和缺失条件，不得跳过整个功能的纯／模拟测试，也不得将缺设备改为伪造连接或成功应答。新增缺项归入既有 `.analysis/results/gaps.json`，不创建平行进度文件。
- **期望值必须独立**：固定报文、参数范围、状态转移与响应样本来自经核实的当前官方源码／二进制或真实对照采集，保留其版本、适用分支及项目相对来源；所属 crate 的 `testdata/` 只保留必要的最小夹具。严禁用被测 Rust 编码器生成其自身期望值，或将按同一猜测编写的模拟器视为独立协议证据。Mock／属性测试工具只提供测试机制，不能证明真实固件行为。
- **传输与业务比较分别验收**：将 Rust 构造的报文交给官方 HID 导出重放，只能验证该输入下的传输结果，不能据此宣称业务命令、参数构造、解析、初始化或产品分支已与官方一致；这些部分必须另有独立预期及对应业务对照。动态字段的比较规则须有官方语义依据，保留原始样本；不得随意忽略字段、放宽容差、重排事件或吞掉差异。差异在查清和处理前保持失败／未验证，已核实的语义差异也须如实记录。
- **读写对照必须恢复状态**：先只读，确认同一实际设备、配置档及完整原值；两边顺序执行，在释放前一会话后再切换。可恢复写入按“记录原值 → 官方写／Rust 独立读回 → 恢复并确认 → Rust 写／官方独立读回 → 恢复并确认”覆盖适用的交叉确认；没有独立 getter 时按已核实的官方完成契约记录比较范围，不能伪造读回。失败、超时或取消仍须执行独立的恢复和清理；无法确认完整恢复能力时不得开始写入。固件刷写、不可逆操作、应用窗口及安装验收继续遵守根目录执行限制。
- **完成度以当前收据为准**：分别记录纯／模拟测试、官方 DLL 实际功能对照、真实设备写回、UI／后台接线及运行时验收。收据必须包含当前 Rust 输入身份、官方输入身份、型号／固件／传输分支、初始状态、用例输入、双方原始输出和解析值、差异、恢复／清理及未执行项；实际一致与两边共同失败分别判断。缺失、零命中、跳过、环境不满足、模拟通过及旧输入快照均不能提升为当前功能完成，现有通过记录不得自动扩展覆盖范围。

- 先检查最终工作树和所属约束，定义能够反驳错误实现的最小证据，再修改。复现不可执行时写明限制，以及静态证据或替代测试实际证明的范围。
- 开发中使用定向 `cargo check --locked -p <crate> --all-targets` 或纯／模拟 `cargo test --locked -p <crate> <filter>`；确认测试数量，零命中不算通过。文档改动检查内容、链接与引用，不因位于 Rust 仓库就编译全量。
- 代码稳定后检查格式与受影响的纯／模拟测试。共享 API 需检查反向依赖；变更涉及全局依赖、生成器、安装配置或影响面不明时，以 `cargo check --locked --all-targets` 核对工作区。不能在每次局部编辑后重复全量检查。
- 顺序问题优先用事件屏障、显式逻辑时间和已有测试接缝复现；不能增加睡眠、重试或放宽断言来掩盖失败。模拟成功、静态解析成功和分析器队列结束分别报告。
- 读取接线须用与本地缓存／默认值不同的模拟设备值验证页面数据入口，并覆盖失败、未知、断开、重连及用户正在编辑的分支；禁止回退到缓存／默认值。写入测试分别核对实际发送、应答、协议要求的读回和状态刷新，不能以文件保存或同一输入的序列化往返作为设备读写通过证据。
- 正式维护入口是 `tools/workspace.py`。通用能力归入现有工具模块及子命令，保留统一收据、gaps 与验证记录；一次性调查放 `.work`，不得积累逐问题脚本或平行进度文档。
- 生成器与消费者共用明确 schema／所有者，完整检查字段、顺序、重复、分支、引用和删除路径；使用当前实际输入字节计算 SHA。生成后回读验证，不能只比较记录数或目录是否存在。
- 静态约束使用现有 Rust／JS AST 工具而非易误匹配的全文替换。规则应在真实工作区路径上验证所有者、其他 crate 调用方、非法副本和无关表达式；宏、别名或动态分支未覆盖时如实列明。
- 整理目录使用 `organize-sources`，核对根入口、全部 crate、平台／测试／构建依赖及嵌入引用。移动文件时同步生成器与清理路径，不用新增空模块维持旧布局。
- 安装器、Cargo 准备和运行时共用安装配置；只从已有且已核验的载荷准备封装，核对架构、普通／延迟导入、资源身份、普通权限缓存位置及升级／卸载边界。准备和静态校验不等于运行安装器验收。
- 汇报给出实际命令、主机／目标、关键结果和证据范围。失败、跳过、dry run、手工审阅、未能执行分别列明；不能声称没有运行的 CI、其他平台或真实窗口／设备已经通过。
- 本规则不增加发布权限。用户已授权的本地 DLL／服务／设备功能测试按 `AGENTS.md` 的实际调用与清理边界执行，分别记录真实调用、返回、对比、恢复与未验证范围；应用窗口、厂商 JavaScript、未授权 helper／installer 仍不运行。资源获取和上传仅按用户已授权的静态资源交付链执行。
