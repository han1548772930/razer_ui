## 实际设备移除通知与断开消费

统一入口 `python tools/workspace.py audit-family-function --family gamepad --function mw --product 2636 --query gamepad-2636-detection-native-chain`；正式证据归 [gamepad-mw-audit.json](../../../../.analysis/results/frontend/gamepad-mw-audit.json) 的 `gamepad_2636_detection_native_chain`。通知的 JS 消费者复用同一收据的 `gamepad_2636_removal_notification_chain`，并沿用已确认的 19 个 Mapping 原生移除函数。本段覆盖实际通知生产、身份传递、断开／重新建立连接的消费者与原生停止边界。

- 当前 onLoad 实际取得 USB／BLE 单例，并订阅 USB disconnected、BLE remove／disconnect；对应加载器明确选择 rzUSB／rzBLE 分块。当前 DeviceInfo 仅声明 PID2636、VID5426、interface1，没有 bleId／dongleId。通用 BLE 订阅不能作为本型号支持 BLE 的依据，产品移除消费者仍要求事件 container 和当前设备 PID 都相等。
- USB 的 JS 生产入口是检测包装器的 registerRemoved 回调，经通用 remove 事件进入 Host initUSB，再把原始设备对象广播给有效窗口并发送到共享事件总线。Host 先启动监视，再附加 add／remove 监听；包装器在原生调用前修改 started 标志，启动抛错不会恢复标志。USB 广播逐窗口捕获发送错误；BLE 的发送循环与本机事件总线共用一个 try，单次发送异常可能阻止后续投递。
- 当前 USB 实例按 VID5426 接受事件，用 PID＋container 串行加锁，不使用 usbInstanceId 或连接代次。移除时先清 notReady 标记和设备缓存，再等待 HID／serial 清理，最后发 disconnected；所选清理封装记录并吞掉 IPC 错误，没有核对清理结果。新增设备先等待 HID 查询重试，但同样不检查其布尔结果，因此这些事件都不能冒充真实设备或清理确认。
- BLE 的共享 JS 生产者来自 Host 蓝牙状态、endpoint 移除及已连接 peripheral 的 disconnect，保留来源 PID／VID／container／mac。当前 rzBLE 按真实 vendor 集合筛选、按 mac 移除缓存；非 poweredOn 状态逐项发移除通知后清空缓存。这里记录实际共享入口，不把其注册或工厂名字推成 PID2636 的传输资格。
- 产品消费者尊重 ignore 标志，清运行时元数据后启动清理但不等待，也不匹配 instance／generation。现有 setup → connectCurrent 仍按产品候选与 container 选择设备，并在重试完成前发布新的 rzDevice；旧工作没有因此自动失效。Host Mapping 同时消费共享通知，其物理移除可绕过页面 URL 最后持有者条件；具体析构／join 继续复用既有移除链。
- preload response 提供取消订阅函数，但这些 provider 没有保留它。USB destroy 只移除非 Electron 的 navigator 监听，BLE destroy 只移除 EventEmitter 监听；所选产品清理也没有显式解除 onLoad 的移除订阅。锁释放、窗口关闭和设备线程 join 都不能证明已派发 Host／renderer 工作排空。

检测 addon 是当前 Host 中 rz-usb-detect 0.0.22 的 x64 detection.node。原件的完整静态捕获已保留，选中通知链的 44 个函数均具备完整伪代码、汇编及原始 PE 字节复核，另核对模块描述符、CRT 注册指针、USB 接口 GUID 和两个设备属性键共 5 处实际 PE 数据。`node_module_register` 经真实模块描述符到初始化函数，再以 V8 模板的 External 数据分发到 `registerRemoved`、`startMonitoring`、`stopMonitoring`；这些入口不是 C 导出函数。单一回调参数会保存为 persistent；重复注册没有释放旧回调，多于一个参数会留下空 persistent，不能自行改写成理想化签名。

原生初始化解析 8 个 SetupAPI 过程、建立两个自动复位事件，并先枚举缓存；缺少库或过程走原版进程退出路径。监视线程注册真实窗口回调与 USB 接口通知。窗口只接受设备接口的 arrival／remove-complete 消息：从广播地址加 32 的 ANSI 文本截去末尾 GUID、替换分隔符并转大写，再与实际枚举所得 instance ID 逐字节匹配。命中后使用 LocationInformation 与首个 HardwareID 拼接的键查缓存；该缓存键、完整设备路径、container 与 `usbInstanceId` 各有不同来源，不能混为一种设备身份。

移除命中缓存时，先完整复制设备记录，再擦除缓存并释放原记录；未命中则建立独立载荷并重新查询。实际 JS 对象包含 `locationId`、VID／PID、`productName`、`deviceContainerId`、`devicePath`、`usbInstanceId`、`manufacturer`、`serialNumber`、`deviceAddress`。名称遵循总线描述／友好名称／设备描述的原版顺序；container 来自设备属性，instance 来自接口路径。此链不读取设备序列号，`serialNumber` 保持初始化空串；`deviceAddress` 是进程内计数器。属性读取失败没有统一成功标志，缓存路径的 VID／PID 还可能未初始化，不能把这些原版载荷当成已确认设备状态。

libuv 的 worker 等待 OS 事件，after-work 在 Node 线程构造载荷并调用 JS；移除载荷在回调返回后释放，再确认通知线程并复用同一请求。stop 先清运行标记、停信号并唤醒事件，再发关闭窗口消息、等待线程和卸载 SetupAPI；正常线程出口解除通知、窗口与窗口类。原版未排空 after-work，也没有释放注册 persistent、两个事件、libuv 信号句柄和请求；CRT 退出清理仅释放缓存树键／节点，不释放设备记录。线程等待通知确认或尚未建立窗口时，stop 的等待顺序仍有静态竞态边界，未经执行验证，不能宣称完全排空或已实测死锁。

`Gamepad2636DetectionNativeChainTests` 11 项定向反例覆盖注册指针、通知身份、缓存复制、全部载荷字段、伪代码遗漏的数值 ABI、排队顺序、停止边界和失效证据拒绝；已有 JS 通知测试继续适用。完整捕获中另有一个未选 CRT 函数 `0x20668` 的 Hex-Rays 失败，原始块、完整汇编和失败记录保留，不能将它计作语义成功；它不构成本链私有数据库的后续依赖。现有 Rust `controller_notification.rs` 处理硬件报告通知，独立 OS 通知实现、真实 UI／后端接线、实际官方对照和运行验收仍分别待完成／未验证。后续只接续 `gamepad_2636_detection_native_chain/remaining_chains` 中已有实际功能关闭链与已取证的重连分支。未执行厂商 JS、应用、DLL 或设备操作；新建的私有分析批次由统一清理流程验收释放，正式原件、捕获与失败证据保留。
