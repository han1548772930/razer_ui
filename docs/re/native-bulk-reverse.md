## 全产品统一逆向执行方案

执行范围由当前官方产品目录、部署入口、MW、主机本地模块及其原生依赖共同确定。前端源集按[输入索引](../../.analysis/inputs.json)及获取收据确认，基础原生索引和历史提取队列各保留自身快照；它们不代表产品数量或语义完成数量。统一清单按实际产品 ID、功能、版本／固件条件、传输和平台分支记录；键盘、鼠标、音频、灯光、手柄、配件、系统、主机本地功能及本机安装生命周期同时纳入，不以单个型号代表整个产品族。

当前 `family_candidate_scope` 的定位集合为 mouse 76、keyboard 73、audio 77、gamepad 9、system 41、accessories 56，去重并集 332；类型化目录注册项为 331，均有唯一 ID，全部包含在定位集合内。唯一额外候选是 mouse 162；[完整身份审阅](../products/mouse/products/162.md)核实其仍可取得的旧部署路径在 UI／MW 两层均声明 DeviceInfo 163，当前实际分类与路由没有 162 注册或别名。该路径继续作为独立部署分支保留证据，不新增一个已注册硬件产品，也不以其能力覆盖 163 的当前部署。定位集合合并当前目录、受维护端点和已保留入口，不能直接把 332 当作均已确认有效的产品数。

1. **先冻结当前版本并建全量分支表，再调度。** 绑定当前稳定部署、版本清单和实际原件字节，从现有原件、产品目录和真实挂载／初始化调用方关联各产品，列出共享链和独有分支。已有完整捕获逐 SHA 复用，只有缺失或变化的依赖进入提取队列。发现官方换版时，独立获取新版本并明确替代范围，保留旧版收据；严格复核期间不覆写该队列引用的原件和捕获。源码不可用、部署失稳、提取失败、语义未闭合分别记录原因，不能混为一个总进度。
2. **共享调用链只分析一次，所有产品逐分支核对。** 以原件字节身份和实际调用方共同确定复用范围，批量处理设备发现／传输、配置档、按键／宏、灯光、音频、摄像头、系统与本地服务链。每个产品仍核对真实 adapter、能力注入、固件条件、默认值和参数；文件名相似、同族型号或相同 getter 不足以复用结论。
3. **四条固定并行主线。** 协调者负责全量清单、跨层接线、差异和最终复核；其余三条分别处理全产品前端／MW 语义、原生协议／驱动／服务，以及音频／灯光／摄像头等专项与证据获取障碍。各主线按共享能力和独立文件分批，空闲后领取下一批，避免多人重复捕获同一模块。当前主机有 16 个逻辑处理器，纯静态解析和验证采用有界进程池；IDA 的并发另外按实际内存、数据库占用与 I/O 控制。以完成的有效任务吞吐、峰值内存和磁盘等待调整并发，避免同时启动重复全库任务造成争用。
4. **失败进入根因队列继续处理。** 获取失败核对当前部署和稳定性；缺 source map 则读取完整现行 JS／CSS 并使用 AST、模块与调用者交叉证明；反编译失败继续核对原始汇编、类型、间接表、函数边界和异常元数据。共享编码、FLS、边界或 SDK 坐标问题按根因批量修复；不同候选通过绑定所有原件和差异的正式审阅裁决。保留原失败及非零收据，未知 ABI 不猜测，不能直接把失败从清单删除。
5. **按完整功能链验收。** 每个范围内功能必须查清状态来源、初始化和读取顺序、观察、输入／计算、真实写包、应答／读回、事件消费者、持久化、失败、取消、恢复和释放，并覆盖实际产品／版本分支。找齐文件、捕获全部函数、静态队列 passed 分别只是证据阶段；不能据此把完整语义标为完成。Rust 实现、UI／后端接线、纯／模拟验证和实际 DLL／设备验收另列状态，受执行限制的运行项保持未验证。
6. **统一发布和清理。** 只使用 `tools/workspace.py`、现有正式审阅收据与 `.analysis/results/gaps.json` 汇总；每批只复核受影响的任务及其依赖，避免重复全库捕获。语义审阅、工具修复和独立新输入获取可在复核期间继续；与冻结输入冲突的发布等待复核结束，再按实际差异接回。正式引用与复现入口接好后，创建者负责临时脚本、私有数据库、克隆及中间产物，按统一清理计划实际释放并记录结果。有效原件、后续源数据库及未决证据继续保留；不新建逐产品的平行进度档案。

领取顺序按依赖和覆盖收益确定：先处理阻断多个产品的共享根因，再成批核对使用该链的全部产品差异，最后收束独有功能。键盘、鼠标、音频、手柄、配件、系统及共享灯光均先完成范围盘点，避免单个型号反复扩展而其他产品没有进入语义核验。某项受阻时，同一主线继续处理无依赖的任务；受阻项保留负责人、原失败、缺失条件和下一条可执行的取证路径。

每批交付实际覆盖的产品／分支、完整调用链依据、已关闭与仍开放的未决项、受影响验证及实际清理收据。完成一个批次后立即领取下一批，全量结束时再对冻结基线统一复核。工期依据已确认的独立功能分支及首批实测吞吐估算，不能直接用文件数、函数数或队列通过比例推算。

汇报单位采用“本批覆盖的产品及功能分支、真正闭合的共享链、仍未解决的具体原因、验证层级和已执行清理”，不得用提取函数数换算全项目完成百分比。全量逆向完成需由上述分支表逐项验收；在剩余语义工作量未核实前，不承诺未经测量的完成时长。

全量执行采用同一冻结基线下的连续批次。先扫清全部范围，再收束全部差异；分支以产品 ID、功能、版本／固件条件、传输及平台组成稳定身份。每个产品必须出现在统一分支表中，已证明的别名、排除项及不适用分支也必须保留依据，包括候选集与目录注册项的身份差额。新增发现归入现有 `gaps.json` 及其所属正式审阅，完成一项即接回清单，避免靠聊天记忆决定下一个型号。

| 主线 | 固定责任 | 批次结果 |
| --- | --- | --- |
| 协调与主机共享链 | 产品身份、全量覆盖、跨层依赖、主机状态／事件消费者、最终复核与清理 | 每个产品都有负责人和可追溯分支；共享结论接到真实调用方 |
| 产品前端与 MW | 键盘、鼠标、音频、手柄、摄像头、配件及系统的挂载、动作和生命周期 | 同一能力的所有实际产品差异一起审阅，独有分支明确列出 |
| 原生协议、驱动与服务 | HID／USB／BLE、间接调用、协议编解码、服务及线程释放 | 输入到真实响应和消费者闭合；反编译冲突逐原始指令裁决 |
| 证据补缺与专项 | 当前部署、缺失依赖、音频／灯光计算及跨产品阻塞根因 | 获取闭包或完整替代证明；根因修复后批量复核受影响输入 |

具体领取可按已完成的能力调整，但每项只有一个发布所有者。当前最多四个智能体同时工作；解析进程池与 IDA 并发另算，不能将进程数当作智能体数。

执行顺序如下，各批完成后直接进入下一批，无须逐型号等待确认：

1. **接续已经结束的严格复核基线。** 950 项严格复核已结束；原队列的任务 ID、完成事实和完整证据保持不变，其中 61 项静态未决已由当前增量收据全部闭合，后续按全量分支表继续产品语义核验。历史收据保存为核验逻辑字节数及 SHA 的无损引用，活动收据不递归嵌入整份旧报告。只重验变化或真实失效的任务及其反向依赖，不能为重新计算总数反复运行全部 950 项。
2. **按共享能力横向扫全产品。** 发现／身份与传输 → 配置档／按键／宏 → 灯光 → 音频／摄像头／系统与配件 → 主机服务和安装生命周期。它是依赖优先顺序，各主线可以同步处理已经具备依赖的能力；每轮每个仍有可执行未决项的产品族至少领取一个批次，受阻族记录具体依赖，不能等待整个键盘族结束后才开始其他族。同批覆盖该链全部实际调用方。已闭合链保留依赖指纹及消费者集合，已有证据充分的 747 仅因新官方分支、依赖变化或失败回归重验，并记录触发证据。
3. **对硬缺口单独补查。** 网络／部署、边界／类型、间接调用、SDK／反编译器、产品语义分别归因。相同输入和相同方法重复失败而无新证据时，必须换取证路径或交叉审阅，并保留下一步行动；不能无期限原样重跑。其余槽位继续无依赖批次。冻结复核结束后，补查结果按依赖有序发布，只重验变化输入和真实反向依赖。
4. **逐分支交叉验收并清理。** 对照产品目录、实际挂载／初始化入口、主机模块和原生依赖核查无人负责、未审阅和漏接分支；再从全部官方本地 UI 动作和原生 dispatcher 分支反向核对完整调用链，不能只勾选已有文档或 Rust 入口。没有来源到消费者的完整链便继续补查，未解析间接调用阻断相应分支完成。每批发布后执行统一清理，验证已删除、保留及失败项和真实占用变化，再领取下一批。

纯解析／严格复核先使用 16 个进程；IDA 补查先最多 4 个独立私有数据库进程，根据实际完成吞吐、内存和磁盘等待调整。二者共用资源预算，不能同时按各自最大值无界启动。耗时任务单独进入有负责人队列，保证短任务与其他产品族继续前进。估时使用闭合的独立功能分支及各类硬缺口的实测处理时间，分别估算剩余工作；全库文件数和 CPU 占用率不作为完工指标。

全量逆向的收尾条件是：当前范围及依赖身份明确，所有范围内产品／版本／传输分支均有完整语义依据，所有间接调用和失败路径均有可复核结论，统一清单中没有未归属或未解释的语义缺口，复核及本轮清理有实际收据。Rust 独立实现、UI／后端接线、纯／模拟测试和实际 DLL／设备对照仍分别验收；缺少运行条件只能使对应实际验收保持未验证，不能抹掉仍未查清的逆向项。

### 调度、里程碑与验收口径

本方案以当前稳定版的一次完整覆盖为目标，通过连续批次推进；新发现必须归回同一分支表，不能在队列清空时跳过刚发现的分支。工作量以经过身份核实的产品功能分支计算。全量分支表和未决项继续由现有 family 审阅、主机审阅及 `gaps.json` 维护，不创建第二份完成清单。

| 里程碑 | 执行动作 | 通过条件 |
| --- | --- | --- |
| 范围无漏项 | 联合目录、部署／挂载入口、MW、主机模块和原生依赖核对 332 个定位候选与 331 个目录注册项 | 身份差额有来源解释；每个范围内产品及其功能／固件／传输／平台分支都有负责人、证据和当前状态 |
| 所有产品族进入语义审阅 | 四条主线按共享依赖并行领取；每轮检查所有仍有可执行项的产品族 | 无可执行产品族因单一型号长期占用而闲置；受阻分支都有具体依赖和下一条取证路径 |
| 完整功能链逐项闭合 | 共享链审阅一次，再核对所有真实消费者及产品差异；同时处理独有逻辑 | 读取、修改、传输、确认、状态消费者和失败／取消／恢复／释放有完整依据，未知间接调用不冒充已解析 |
| 失败根因批量收束 | 将原件获取、解析、反编译器、类型／栈、间接调用与语义缺失分别处理 | 每个失败有保留的原始事实和可复核结论；原始汇编证明与伪代码恢复分别记录，不强求用伪代码替代完整语义证明 |
| 全量交叉验收 | 从官方 UI 动作向下、从 native dispatcher／本地服务事件向上核对分支表 | 双向核对没有无人负责、漏审或漏接的范围内链路；受影响复核通过，逆向语义未决归零 |
| 批次清理完成 | 正式证据接线后，通过统一入口重新核实并实际执行清理计划 | 删除项确认不存在，保留项仍可复核，失败有原因，实际释放空间有收据；清理计划不能充当执行结果 |

每个领取任务必须指明分支身份、所需输入、实际消费者、预期产物和发布所有者。共享依赖按可解锁的真实消费者数量优先，同等依赖条件下兼顾尚未审阅的产品族；长耗时补查单独排队，不能占住全部槽位。每 30 分钟检查有效吞吐、依赖阻塞、内存和磁盘等待并调整任务分配，不因到达检查时间中断有效分析或把未决项视为完成。相同输入和相同方法没有新证据时不得盲目重试；应换完整汇编／类型／交叉引用、当前依赖获取或独立交叉审阅路径，同时继续其他可执行工作。

当前各线从已有成果接续：协调线核清共享 mapping descriptor 的存储、分类与消费者，并接回全部适用产品；前端线收束手柄和摄像头当前审阅后，按全量分支表继续所有产品族；原生线批量处理 NLG、x87、间接调用和栈分析等共享根因，再定向复核受影响输入；证据与专项线接回当前前端依赖修复、音频命令与生命周期语义，再领取仍缺来源或共享计算依据的分支。这些是首批入口，不是全量任务清单，完成后自动领取下一批。

每轮只汇报有证据的产品功能分支、共享链、剩余根因和实际清理结果。首次全族覆盖完成后，才按已闭合分支吞吐与剩余根因实测成本给出工期区间；证据获取、逆向语义、Rust 实现、UI／后端接线、纯／模拟验证和实际验收分别报告，不合成为一个误导性的完成百分比。
