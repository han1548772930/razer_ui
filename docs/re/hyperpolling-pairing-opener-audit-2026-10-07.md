# HyperPolling pairing utility opener audit

Product 179's current Dashboard bundle (`.ref/devices/179/static/js/main.4849f7ca.js`, opener near offset 4,105,355) does not open a standalone `multiDevicePairing` root. It reads the first paired entry's `productId`, resolves the target MW/UI window names through the host window service, focuses that product UI, then broadcasts `TAB_PERFORMANCE` for keyboards or `TAB_CUSTOMIZE` for mice. The 179 root selector has only `macro`, `armory`, and default branches; `display-mode-roots.json` does not register 179 for `multiDevicePairing`.

The local HyperPolling row currently emits a unit `SourceControlsPairingRequested` event, which the workspace turns into `PairingRequested` for product 179 itself. The shell then tries the standalone pairing root and rejects 179, so the action is a dead end. The receiver pairing state cannot currently supply a safe target for this click: bindings are queried only when the receiver modal opens (`src/features/source_controls/receiver_pairing_view.rs`), `query_receiver_pairing` stores the returned raw receiver PID in `ReceiverPeer::queried` (`src/shell/device_discovery.rs`), and that peer has no edition, serial, or category metadata. The click does not carry a peer identity, and the official host window service is not part of the local route.

Do not route this action using the raw PID or infer a target category. A faithful local implementation requires a source-verified read observation that maps the paired receiver entry to a unique product workspace and category, plus an available target workspace. Until that observation path exists, the generic standalone pairing-window request must not be presented as a working 179 opener.
